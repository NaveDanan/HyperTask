## Native navigation contract

`HyperConnectionSelection` is a discriminated union for list, new, broker directory, app, tool and Bot pages. `HyperConnectionNavigationProps` exposes optional `selection`, `onSelectionChange` and `onConnectionStarted(serverId)`. `hyperConnectionSelectionFromPath` maps original admin and personal nested paths, discarding query and fragment data. `HyperConnectionsPanel` and admin `HyperPluginsSection` accept the props. Parent may use these for links and Back navigation.

Parent main must own the external callback, consume any provider-returned callback credentials there, and navigate with the server/app ID only. The renderer starts consent in the system browser and offers server confirmation; it never treats browser return alone as connection success. Callback credential delivery is a parent integration dependency, not implemented in this owned folder. No renderer callback credential reader is exported.

Consent completion has not been exercised against a live vendor, as prohibited. App request components are exported; parent Bot/chat areas must mount them where their upstream card equivalents appear. The local selected-Bot plugin page mounts the action directly. Arbitrary multi-Bot/multi-tool batches have explicit selection, read/write/destructive labels, operation counts, confirmation, shared approvals, sequential progress and refresh after partial failure.

Integration corrections bind pending shared approvals and late exposure reads to the displayed app/Bot/tool scope. Navigation invalidates them, the dialog names its Bot, and stale confirmation callbacks cannot grant another target. Shared broker sign-in completion is offered to admins through the original confirmation endpoint; its server resolver chooses the deployment account and enforces admin permission, with no client-supplied holder. Live vendor consent remains separate acceptance.

The scope also expires when the component unmounts. Every grant/revoke write, including read-only bulk and multi-Bot batches, checks the current scope immediately before HTTP. Leaving during an exposure read or between sequential writes stops further mutations; previously accepted writes remain and authoritative refresh reports their state.

Account-mode previews and destructive panel actions are tied to an app/navigation epoch. Incoming route changes reset confirmations without dropping a matching destination's credential form. Preview results from an older target cannot be applied to another app. Server-reported broker configuration gates automatic confirmation on arrival/remount and once on focus after consent; this calls the original status confirmation endpoint, not key recheck. Only admins confirm shared accounts, whose holder remains server-resolved. Failed confirmation shows recorded state and generic retry guidance, never assumed success or an invented absence.

`HyperAccessRequestList.ts` is a native lifecycle adapter shared by the app and shared-account inbox lists. Each mounted app selection owns its rows and read generation. Changing the app hides old rows before effects run; late reads cannot replace the new app's result. Decision callbacks recheck the scope and current row before entering the parent runner and immediately before HTTP, so cached/deferred buttons cannot approve another target or act after unmount. Valid approve/dismiss/decline still use the original endpoints and reload the current list. Old settlement cannot start another read for the abandoned app. No credentials or owner binding are stored here.

The Bot app-access card also scopes its snapshot, read generation, busy/error feedback and callbacks to the mounted Bot/app/admin selection. This replaces unscoped local state while preserving pinned `botAppQueryOptions(agentId, app)`'s name-or-key request contract. Changing selection hides old state immediately; unmount and old read generations cannot publish results. Mutations, setup navigation and Refresh require the current snapshot and scope. A pending mutation's settlement cannot start a read for an abandoned selection. Current actions and generic retry feedback remain available; backend permissions remain authoritative.

Shared-audience editors use `useId` for an instance-specific radio-group name. Multiple Bot editors in the account-mode confirmation cannot deselect each other's radios while retaining an unseen exposure value. Server-proposed membership and original approval payloads stay unchanged.

Grant lifetimes now use opaque arrival objects plus operation epochs, rather than reusable selection strings. Returning A-to-B-to-A or canceling a dialog invalidates old reads/confirmations and later sequential writes. Shared single and read-bulk operations load that Bot's actual needed exposure; batches review and send a separate server-proposed exposure per Bot. Malformed held-app proposals refuse the operation. An unheld app requires explicit confirmation that its first grant will resolve current exposure on the server, without substituting owner-only or another Bot's members. Already accepted writes are not reverted. The app-access card follows pinned `components/channels/app-access-card.tsx` refusal semantics: reconnect/shared can override stale ready, only a strictly newer connection clears that override, and shared refusals create no duplicate access request.
