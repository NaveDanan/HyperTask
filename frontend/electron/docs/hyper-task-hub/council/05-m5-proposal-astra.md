# Astra's M5 proposal

## Summary

I would ship Jira transitions with a native confirmation for one issue and one transition. Newsletter status stays in its editor until its server offers an authorized, conditional task edit. A timeout buys a read, never a second send. Board and Matrix moves belong to the personal ledger. The largest integration risk is the legacy Jira credential bridge available in the application renderer. The largest calendar risk is assuming the Hub's seven-day cache covers Hyper-Event's month view. Paths below are relative to `frontend/electron`.

## 1. Write-back architecture

Add a main-owned status service beside the read adapters. Start from one source handle on the card, even when two Jira issues share a merged action. Main resolves the handle, checks its generation and expected snapshot revision, and requires a currently selected, accessible origin or assignment. A mention, mirror or article cannot be the write target. Add separate Jira and Newsletter opt-ins to setup and Settings, both false for new and existing partitions. Bind consent to the configured connection and clear it on replacement. Turning either switch off invalidates that source's outstanding approvals. The existing contract already ties a handle to one piece of evidence, and setup changes retire the active service. See `src/shared/HyperTaskHub.ts:110`, `src/main/hyper-task-hub/HyperTaskHubService.ts:385` and `docs/hyper-task-hub/council/03-consensus-spec.md:76`.

```ts
type HyperHubRequestVersion = { scopeGeneration: number; expectedRevision: number }
type HyperHubWriteSource = 'jira' | 'newsletter-task'
type HyperHubStatusChoice = {
  choiceId: string; transitionLabel: string; targetStatus: string
}
type HyperHubStatusPreview = {
  token: string; expiresAt: HyperHubInstant; source: HyperHubWriteSource
  accountLabel: string; site: string; targetLabel: string; targetRevision: string
  before: string; choice: HyperHubStatusChoice
}
type HyperHubWriteView = {
  operationId: string; evidenceId: string; state: 'pending' | 'succeeded' | 'failed' | 'unknown'
  observedAt?: HyperHubInstant; observedStatus?: string; reasonCode?: string
  undoAvailable: boolean
}
interface HyperHubStatusCommands {
  statusOptions(v: HyperHubRequestVersion & { handle: string }): Promise<HyperHubStatusChoice[]>
  previewStatus(v: HyperHubRequestVersion & { handle: string; choiceId: string }): Promise<HyperHubStatusPreview>
  approveStatus(v: { token: string }): Promise<HyperHubWriteView | 'cancelled'>
  previewStatusUndo(v: HyperHubRequestVersion & { operationId: string }): Promise<HyperHubStatusPreview>
}
```

Use strict schemas and typed rejection envelopes around those success payloads. Append channels `hyper-task-hub:status-options`, `:preview-status`, `:approve-status` and `:preview-status-undo` under the existing prefix. Only main has an execute method. A preview resolves current identity, source revision and permissions online. Its random, single-use token indexes an in-memory record bound to the originating window/document, partition, generation, credential fingerprint, principal, native target ID, before-status ID, revision, transition ID, destination ID, required-field signature and a monotonic 60-second deadline. Main constructs both displays from that record. Preview expiry, cancellation, navigation, shutdown or revocation discards it. Existing channel, sender and revision checks provide the entry point. See `src/shared/HyperTaskHub.ts:382` and `src/main/hyper-task-hub/HyperTaskHubIpc.ts:180`.

Approve reserves the token synchronously and opens one window-modal native dialog. Cancel is the default. The explicit affirmative button names the source. After affirmation, serialize by partition and target. Re-resolve the live credential and principal, scope membership and selection. Fetch the immutable issue ID with status, project, assignee/reporter and `updated`, and fetch expanded transitions afresh. Compare the bound values, recheck expiry and window after awaits, then durably claim the operation before dispatch. Immediately recheck the local generation/lease and dispatch once with the bound credential. Any mismatch requires a new preview. Borrow the destination comparison and single-winner claim from Bots, with a Hub-owned journal and strictly per-item approval. See `src/main/HyperBotsRuntime.ts:923`, `src/main/HyperBotsStore.ts:569`, `src/main/HyperBotsHttpTools.ts:102` and `src/main/hyper-task-hub/HyperTaskHubStore.ts:129`.

Append claim and terminal events under one operation ID in the encrypted ledger. Record local owner and source principal, time, connection and opaque target identity, before status/revision, requested after status, result, observed after status/revision when known, and any inverse operation ID. Minimize stored labels, purge source-derived text under D3, and suppress inaccessible targets in projections. Cache clearing preserves the audit. A failed claim persistence prevents sending. An unterminated dispatch claim on recovery becomes unknown. A receipt arriving after a switch may settle only its original partition via a serialized journal update, never publish into the new one. The store already separates cache clearing and account/workspace partitioning. See `src/main/hyper-task-hub/HyperTaskHubStore.ts:147`, `src/main/hyper-task-hub/HyperTaskHubStore.ts:185` and `src/main/HyperBotsStore.ts:597`.

Project `writes?: HyperHubWriteView[]` separately from observed source statuses. Pending means confirmed and in flight. A documented success acknowledges the write; a targeted GET supplies the resulting revision and updates the chip. A definitive rejection shows failed. Timeout, broken response, ambiguous server error or crash after dispatch shows “Outcome unknown. Check in Jira.” Block another send for that operation. Reconcile by a targeted read, including closed issues outside the open-work query. Display what the read actually found. Matching status alone cannot establish who made the change. Preserve uncertainty in the audit unless source history settles attribution. Keep a recent operation accessible when the card leaves the board. Offline, cached tasks and local actions work; external preview, approval and Undo require a connection. There is no offline write queue. See `src/main/hyper-task-hub/HyperHubJiraSource.ts:26`, `src/main/hyper-task-hub/HyperTaskHubService.ts:202` and [RFC 9110 §9.2.2 on retrying requests](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2).

Source Undo starts from an acknowledged entry with a verified after revision. Read the target again and require that same status and revision, current scope and permission, and a valid reverse transition. Let the owner choose among multiple reverse transitions. Issue a new preview and native confirmation, and append a new linked result. Never implement source Undo through the existing local feedback reversal.

## 2. Permission discovery and concurrency

For Server 8.20, a successful transition returns 204 with no issue document. That makes the post-write GET necessary for the after revision. A 404 can also mean the caller cannot see the issue. Present “Issue unavailable” without revealing its prior title. [Jira Server 8.20.1 REST reference, Get transitions and Do transition](https://docs.atlassian.com/software/jira/docs/api/REST/8.20.1/#issue-doTransition)

**Jira.** Resolve the signed-in user's configured credential and verify the server principal via `/rest/api/2/myself`. For this issue call `GET /rest/api/2/issue/{key}/transitions?expand=transitions.fields`. Show the workflow action name alongside its destination. Require well-formed IDs, destination, and field metadata; send only `{transition:{id}}`. Any required user field, unresolved metadata or unsupported screen goes to the Jira editor. Optional `mypermissions?issueKey=…&permissions=TRANSITION_ISSUES` can explain an empty menu. A positive project permission cannot authorize a particular transition. Cache menu hints in memory for at most 30 seconds keyed by identity, connection, generation, issue ID and revision. Invalidate on denial, edit, refresh that changes revision, or connection change. Always bypass hints for preview and execution. See `src/main/HyperBotsConnectors.ts:23`, `src/main/HyperBotsJiraTools.ts:70`, `src/main/hyper-task-hub/HyperHubJiraSource.ts:65`, [Atlassian's issue transitions API](https://developer.atlassian.com/server/jira/platform/rest/v10000/api-group-issue/) and [issue-context permissions API](https://developer.atlassian.com/server/jira/platform/rest/v10007/api-group-mypermissions/).

Jira's last status/updated read detects intervening edits up to that read. Another client can still act before Jira evaluates the POST. Jira evaluates workflow conditions on receipt; the documented transition request supplies no atomic expected-updated comparison. Treat a rejected transition as a conflict or denial, refresh, and offer a fresh choice. Never invent an `If-Match` guarantee. See [Atlassian's transition request](https://developer.atlassian.com/server/jira/platform/rest/v10000/api-group-issue/) and [RFC 9110 §13.1.1 on origin-enforced preconditions](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1).

**Newsletter.** The setup guide calls for a Newsletter & Gantt authoring token with Read and write for edits, and identifies Newsletter manager, general manager or administrator for Gantt access. The connection verifies `/api/v1/authoring/status` and retains only a Gantt boolean alongside the protected credential. Project GET returns resources and roles; the Hub filters by owner-selected resource IDs. None of these establishes that the token's principal can edit this task in this project. I found client contracts and setup documentation in this checkout, but no Newsletter server handler defining effective project edit authority or a conditional task PATCH. See `docs/HYPER_BOTS.md:25`, `src/main/HyperNewsletterConnection.ts:47`, `src/main/HyperNewsletterConnection.ts:80`, `src/main/HyperBotsNewsletterTools.ts:118` and `src/main/hyper-task-hub/HyperHubNewsletterSource.ts:62`.

Project PATCH accepts a complete chart plus `expectedUpdatedAt`. Its input bounds tasks and enumerates their fields. The Hub also deliberately drops unrelated task content. Rebuilding a project from either representation risks losing other people's work even with the correct timestamp. Use “Open in Newsletter. This server cannot safely update a single task from Task Hub.” Disable the Newsletter opt-in with that reason on current servers. To enable it later, require verified principal and effective project/task edit capability under the actual token, and an atomic server-side task update conditioned on the expected chart revision. Validate a stale-revision rejection and preservation of siblings, roles, progress and unknown fields against the deployed API. Recheck on each approved change. For either source, 401/403 displays “You don't have permission”, clears hints, and offers connection settings or the editor where accessible. A write denial alone does not revoke proven read permission; independently verify read access and purge if lost. See `src/main/HyperBotsNewsletterTools.ts:19`, `src/main/HyperBotsNewsletterTools.ts:141`, `src/main/HyperBotsNewsletterTools.ts:161` and `src/main/hyper-task-hub/HyperHubNewsletterSource.ts:39`.

## 3. Status mapping and Board flow

Keep “My state” and the exact source label together. Jira category keys `new`, `indeterminate` and `done` suggest Next, In progress and Done respectively for explaining destinations. Waiting has no universal Jira transition. Preserve current assigned/reporter defaults and any personal override. For Newsletter, pending suggests Next, in-progress suggests In progress, completed suggests Done. Delayed describes schedule slippage; show “Delayed” and leave Waiting to the owner. Show progress as supplied, including contradictory values; 100% alone cannot complete a task. Never send progress alongside status. Board drag records only local feedback. Put “Change status in Jira…” on the particular source row, available equally by keyboard. A drop should not open an approval dialog. See `src/main/hyper-task-hub/HyperHubJiraSource.ts:87`, `src/main/hyper-task-hub/HyperHubNewsletterSource.ts:135`, `src/main/HyperBotsNewsletterTools.ts:19`, `src/shared/HyperTaskHub.ts:150` and `docs/hyper-task-hub/council/03-consensus-spec.md:283`.

## 5. Security boundary

Transport accepts only fixed operation types, validated identifiers and the configured site. Use the connector's manual redirect handling, omitted ambient credentials and bounded response reads. Return enumerated error reasons to the renderer. A remote error body may contain private data even after credential redaction. Keep raw bodies, fingerprints and authorization headers in main. See `src/main/HyperBotsHttpTools.ts:20`, `src/main/HyperBotsHttpTools.ts:49` and `src/main/HyperBotsHttpTools.ts:64`.

A compromised document can request a preview and open a prompt. Only a genuine response to the main-owned native dialog authorizes dispatch. Use fixed buttons, safe default focus, bounded plain-text details, separate identity and status lines, isolated identifiers and stripped control characters. Never interpolate source text into button captions. Keep tokens out of snapshots, URLs and logs. An inbound IPC boolean, DOM click or bot approval is insufficient.

There is a wider release condition. The shared renderer already has Jira credential reads and Bots decisions on its preload; the credential handler returns the saved value. A Hub-only IPC check cannot protect that whole renderer. I propose a sandboxed Hub document with a minimal preload, a distinct origin and main-enforced sender allowlists on legacy credential, generic core and bot channels. Opening source editors transfers to their established trusted context. Restrict Hub navigation, opener access and network egress; verify the isolation for embedded Hub entry points too. If the owner requires protection against compromise of the entire app renderer, migrate legacy credential retrieval and all alternate status paths to main-owned authorization before claiming that guarantee. See `src/preload/index.ts:113`, `src/preload/index.ts:246`, `src/main/settings-ipc.ts:27` and `src/renderer/features/jira/data/jira-credential-store.ts:14`.

## 7. Risks and questions for the owner

Can the Newsletter maintainers expose effective task edit permission and a guarded status endpoint? Until then the editor is the supported route. Does the threat model include every existing Jira/Bots renderer, including the source editor, or specifically the document presenting Hub content? That choice determines the size of the credential migration. Jira workflow post-functions can also have effects beyond status. Show the transition name and test representative workflows before enabling a connection.

## Positions I hold strongly

Approval belongs to one exact transition. An unknown outcome deserves a targeted read. Neither a partial chart nor an assignment role justifies a Newsletter write. A shared board row needs a durable identity and safe Undo.

## Where I am flexible

The 60-second preview lifetime and Matrix cutoff can change after usability testing. I would also accept a server-proven lossless chart transaction if its authorization, revision and single-field effects can all be demonstrated.
