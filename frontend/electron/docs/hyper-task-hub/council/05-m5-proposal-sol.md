# HyperTaskHub M5 proposal · Sol

## Summary

- Keep the Matrix grounded in D6. A manual quadrant changes the Matrix only and has local Undo.
- Show actual plan blocks, source dates and verified dependencies in Timeline. Group verified meetings by the owner's civil day.
- Preview weights against one frozen ranking input and save only on Apply.
- A source status change requires a fresh preview and a native confirmation. Board drags stay local.
- Use Jira's workflow transitions. Offer Newsletter writes when the server can guard a status-only change atomically.

Repository citations below are relative to `frontend/electron/`.

## 1. Write-back architecture

Use a main-owned `HyperTaskHubWriteback` coordinator, separate from local feedback and the bot tool registry. Add `previewStatus({ scopeGeneration, expectedRevision, sourceHandle, intent })` and `approveStatus({ previewId, candidateId })` to the typed Hub API. Intent is a Hub state or a ledger entry to reverse. Preview resolves exactly one authorized source reference, even on a merged card, and returns an opaque ID, expiry, issue or task identity, configured account, current status and source version, and exact candidate actions and destinations. Main binds the candidate to that preview. Approve opens a native confirmation. After approval, main rechecks and executes without a separate execute IPC. Reuse the validated registration, guarded store commit, and connection-bound HTTP transport. [`HyperTaskHubIpc.ts:180`](../../../src/main/hyper-task-hub/HyperTaskHubIpc.ts#L180), [`HyperTaskHubStore.ts:129`](../../../src/main/hyper-task-hub/HyperTaskHubStore.ts#L129), [`HyperBotsHttpTools.ts:41`](../../../src/main/HyperBotsHttpTools.ts#L41).

Serialize sends per configured account and source target across workspaces. Revalidate scope, opt-in, credential binding, actor, target identity, source version and exact candidate immediately before sending. Jira uses a fresh by-ID read of `updated`, status ID and category, plus a fresh transition list. Then POST the approved transition ID alone. The documented transition API supplies workflow validation, and the read/POST pair leaves a race with external writers. Prefer origin-specific transitions. Route global or origin-ambiguous transitions to Jira unless a deployment can enforce the expected origin server-side. Verify support on the target server since some versions omit origin metadata. Treat version or candidate drift as a conflict and require a new preview. Extend the current targeted Jira check, which reads `updated` for version checks. [`HyperHubJiraSource.ts:118`](../../../src/main/hyper-task-hub/HyperHubJiraSource.ts#L118), [Jira Data Center REST API, issue transitions](https://docs.atlassian.com/software/jira/docs/api/REST/8.20.2/).

For Newsletter, prefer a task-status operation that compares a server-issued chart revision atomically with the update and preserves every other field. The existing task PATCH has no guard. The chart PATCH accepts `expectedUpdatedAt`, but the Hub's reader strips task fields and filters the inventory. Whole-chart replacement is defensible only with a fresh, authorized and lossless chart, demonstrable atomic rejection of a stale revision, and a server guarantee that only the intended status changes. I would ship “Open in Newsletter · safe status updates unavailable” until a status-only guarded endpoint or those guarantees exist. A client hash or a chart reread cannot close the race. [`HyperBotsNewsletterTools.ts:141`](../../../src/main/HyperBotsNewsletterTools.ts#L141), [`HyperHubNewsletterSource.ts:62`](../../../src/main/hyper-task-hub/HyperHubNewsletterSource.ts#L62).

Persist a pending record before dispatch, with app and source actor, timestamp, scoped target, approved before and after, source versions and command ID. Journal the result and publish it by source reference. Treat a definite rejection as failed. Treat timeout, connection loss with possible dispatch, ambiguous reply, or interrupted pending entry after restart as unknown. Never replay. A targeted authorized read settles the observed state, including Jira Done issues that leave the import query. Record the transport outcome separately from observed status. A matching destination without proof of authorship can settle the card's status while the audit records uncertain attribution. A stale read or a read that might precede a late commit leaves the hold in place. Keep “Check in Jira/Newsletter” while the state is unverified. Offer source Undo only when an attributable change still matches its recorded after-version and exact status and a valid reverse action exists. Undo goes through a new preview and approval. Offline keeps the local actions and cached data available. No queue of remote writes. [`HyperHubJiraSource.ts:8`](../../../src/main/hyper-task-hub/HyperHubJiraSource.ts#L8), [`HyperTaskHubService.ts:127`](../../../src/main/hyper-task-hub/HyperTaskHubService.ts#L127).

| Snapshot outcome | Ranking, plan and readiness |
| --- | --- |
| Pending or unknown | Display the last observed source status with the write outcome. Retain ranking facts. For planning and actual readiness, temporarily hold the target and treat its authoritative completion as uncertain. This also protects dependents during a reopen. Keep fixed reservations visible and exclude held blocks from forecasts. A held explicit prep task cannot establish Prepared and a held block cannot establish Planned. Owner confirmation still counts. Remove a newly ineligible “Do this first” immediately and recheck Start in main. |
| Succeeded | Merge only verified readback into the authorized observation. Recompute ranking, forecast and brief readiness. Completion unblocks successors only if the written reference is authoritative for that card. Respect existing local decisions and keep both statuses visible. |
| Failed | Show the reason, lift the hold, and recompute from the last valid observation or fresher conflict read. Scope loss takes precedence over any result. |

Apply holds to execution eligibility and prep inputs, while keeping D6 points based on observed facts. The service already runs the ranker and planner together, uses authoritative completion for explicit prep, and rechecks feasibility on local Start. ## 2. Permission model

Default both source toggles off. For Jira, resolve `/myself` using the configured credential and check issue-scoped Browse Projects and Transition Issues with `mypermissions`. Project permissions are advisory at project scope. Offer only current issue transitions returned with `expand=transitions.fields`. Send screen-required fields and insufficient transition metadata to the source editor. For Newsletter, require server-reported project edit capability covering the task, under the configured token and Gantt role. Resource assignment, listed roles and read access confer no edit capability. If the deployment exposes no trustworthy capability metadata, use the source editor. [`HyperHubJiraSource.ts:63`](../../../src/main/hyper-task-hub/HyperHubJiraSource.ts#L63), [`HyperNewsletterConnection.ts:52`](../../../src/main/HyperNewsletterConnection.ts#L52), [Jira issue-context permissions](https://developer.atlassian.com/server/jira/platform/rest/v11002/api-group-mypermissions/), [Jira Data Center REST API, transition metadata](https://docs.atlassian.com/software/jira/docs/api/REST/8.20.2/).

Cache discovery hints for 60 seconds in main by account, connection binding, target and source revision. Invalidate on scope or credential change, opt-out, revision drift and authorization error. Preview and execution use live checks. Show disabled reasons for offline, disabled by owner, missing permissions, unavailable workflow action or unsupported server. A 401/403 shows “You don't have permission” and clears the permission hint. Preserve read access only where independently authorized. Keep the source-editor action where the owner can still open the record.

## 3. Status mapping

| Hub | Jira source hint and desired destination | Newsletter status |
| --- | --- | --- |
| Next (`ready`) | `new` | `pending` |
| In progress (`doing`) | `indeterminate`, excluding configured Waiting IDs | `in-progress` |
| Waiting | A connection-scoped explicit Waiting status ID in an open category. Without one, Waiting is local. | `delayed` |
| Done | `done` | `completed` |

Source status seeds local state where no local decision exists. Keep reported-only Jira work Waiting while open and preserve the raw status and category on each reference. Missing or undefined categories yield unknown source completion. Newsletter progress is independent metadata, an integer from 0 to 100 when supplied. Status determines completion. Show inconsistent values and preserve progress in the request. If a workflow requires changing progress to accept a status, use the source editor. Current Jira ingest retains the label and seeds by assignment. Newsletter already retains status and seeds Done or In progress. [`HyperHubJiraSource.ts:63`](../../../src/main/hyper-task-hub/HyperHubJiraSource.ts#L63), [`HyperHubNewsletterSource.ts:117`](../../../src/main/hyper-task-hub/HyperHubNewsletterSource.ts#L117), [`HyperBotsNewsletterTools.ts:19`](../../../src/main/HyperBotsNewsletterTools.ts#L19), [Atlassian status category keys](https://developer.atlassian.com/server/jira/platform/jira-issue-statuses-as-lozenges/).

For a requested state, choose only returned, field-free, origin-safe transitions to matching status IDs or categories. Skip self-transitions. For Undo require the exact previous status ID. One candidate can be preselected, several require a choice by workflow name and destination, and zero goes to the source editor. A Board drag between accepted states may suggest “Preview Jira status change” in the local Undo toast, without fetching a preview or opening confirmation. The same offer fits explicit Start and Done for me. Triage, reranking, scheduling, Matrix drags and sync generate no offers. A card menu gives a separate source action without changing the local state. Closing or rejecting a preview leaves the independently requested local action in place.

## 4. Other M5 items

**Matrix.** Use `HyperHubRanked.urgency`, `importance` and `unknown`. Urgent means urgency ≥ .50, or at most 240 minutes of slack. The engine uses the earliest confirmed due or prep deadline, with civil dates ending at the next midnight. At or past the deadline urgency is 1, even without effort. For a future deadline, slack is covered free working time minus recorded effort. Missing deadline, missing effort, or incomplete coverage makes urgency unknown. Mark stale or owner-declared slack provisional. Important means importance ≥ .67. The owner's priority, including zero, wins over mapped Jira priority. Keep all four high/low combinations. For either unknown axis, put the card in “Needs details”, retaining the known axis. Waiting and blocked items keep their coordinates and blocker reason. Review, Dismissed and Done stay outside Matrix. The four quadrants borrow the two-axis Eisenhower practice. Their labels describe the task and confer no permission to start, delegate or delete it. [`HyperPriorityEngine.ts:20`](../../../src/shared/HyperPriorityEngine.ts#L20), [`HyperDayPlanner.ts:111`](../../../src/shared/HyperDayPlanner.ts#L111), [`HyperDayPlanner.ts:430`](../../../src/shared/HyperDayPlanner.ts#L430), [Asana's Eisenhower matrix guide](https://asana.com/resources/eisenhower-matrix).

Drag or keyboard move records `set-matrix-quadrant`, with task ID, chosen quadrant and prior override through the local ledger. Undo restores that override or automatic placement. The override persists through sync and weight changes and leaves scores, priorities, deadlines and plan eligibility intact. Within a quadrant use rank position, then code-unit ID. Apply D9's pointer and keyboard stability to automatic moves and reorderings, with the shared-ID move count, Apply and 10-second idle behavior. Apply the owner's move immediately and reconcile on rejection. Revocation and eligibility changes bypass the delay. Reasons use codes and facts, for example “4 hours of slack” / “נותרו 4 שעות מרווח”, “Effort needed to calculate urgency” / “נדרשת הערכת מאמץ לחישוב הדחיפות”, and “Moved by you” / “המיקום שונה ידנית”. Isolate times, issue keys and mixed-direction titles. [`HyperTaskHubService.ts:594`](../../../src/main/hyper-task-hub/HyperTaskHubService.ts#L594), [`HyperTaskHubSelectors.ts:290`](../../../src/renderer/features/hyper-task-hub/state/HyperTaskHubSelectors.ts#L290), [`HyperTaskHubReasons.ts:274`](../../../src/renderer/features/hyper-task-hub/state/HyperTaskHubReasons.ts#L274).

## 5. Security

Bind a single-use, 60-second preview to its main-frame sender, window, generation, account, credential binding and exact candidate. Consume it when opening a main-owned modal, default Cancel, with one active confirmation per window. A compromised renderer can request the dialog, but only the native confirmation can approve what main displays. Expiry, navigation, scope change and opt-out invalidate the dialog and candidate. Strict IPC schemas accept handles and enums, never URLs, arbitrary fields or an approval flag. Main sanitizes untrusted labels as bounded plain text, isolates mixed-direction content and keeps credentials and raw server errors out of IPC. No bot, model, bulk command or drag can call the send path. [Electron IPC sender checks](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages), [Electron native confirmation](https://www.electronjs.org/docs/latest/api/dialog).

## 7. Risks and owner questions

Can Newsletter expose the guarded status operation under ordinary user credentials? Which Jira workflows need global transitions or mandatory resolution fields? Jira post-functions can also produce server-side changes beyond the requested status. Confirm the source-editor fallback for workflows with unreviewed side effects and whether the owner wants explicit Waiting status mappings in M5. Validate the Jira recheck race against the target deployments. Confirm whether Hyper-Event already has an independently authorized Outlook scope that must survive Hub setup opt-out. [Atlassian's example of a resolution post-function](https://support.atlassian.com/jira/kb/clear-the-resolution-field-when-an-issue-is-reopened-in-jira/).

## Positions I hold strongly

Unknown urgency deserves its own visible state. Keep quadrant changes local. A timed-out write never releases a dependency or earns a replay. Newsletter must prove its concurrency guard.
