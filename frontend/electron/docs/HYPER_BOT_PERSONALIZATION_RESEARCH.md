# Hyper-Bot Memory and Soul research

Research date 2026-11-27

Give each bot an owner-edited Soul and a small, editable Memory. Soul defines the bot's role and how it speaks. Memory holds current preferences and durable facts with a source and a scope. Start with explicit saves and corrections, narrow recall, and a way to inspect what the bot used. A later release can suggest memories from owner messages once the app can prove that suggestions stay out of prompts until accepted.

The implementation includes optional suggestions because it can keep them in a review queue and prove through runtime tests that only approved entries enter the prompt. The existing instructions still define the bot's role. Soul adds four editable style preferences. Memory holds personal defaults for the account and bot, with recall limited to that bot's direct conversations. Workspace-specific project facts are outside that profile. See the [implemented controls](HYPER_BOTS.md#memory--soul).

## What the studies measured

**Recall.** LongMemEval tested 500 questions covering extraction, reasoning across sessions, temporal reasoning, knowledge updates, and abstention. Its retrieval experiments found gains from adding facts to search keys and using time constraints. LoCoMo tested question answering, event summarization, and dialogue generation across long conversations. Lost in the Middle found that model performance could drop when relevant information was buried in the middle of a long input. Together these results support comparing Hyper-Bot's current recent-room context with a small selection of relevant memories. [LongMemEval, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/d813d324dbf0598bbdc9c8e79740ed01-Paper-Conference.pdf) · [LoCoMo, ACL 2024](https://aclanthology.org/2024.acl-long.747/) · [Lost in the Middle, TACL 2024](https://arxiv.org/abs/2307.03172)

**Preference following.** PrefEval tested both stated and implicit preferences across 20 topics. PersonaMem asks which response fits the user's current profile after a series of simulated conversations. PersonaMem-v2 reports 55% accuracy with a trained memory system using 2,000 tokens of readable memory. Its full-history baseline used 32,000 tokens. The result makes a compact profile worth testing, and the accuracy leaves plenty of room for wrong guesses. Hyper-Bot should treat an inferred preference as a draft until the owner confirms it. [PrefEval, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/28a46044775d97a4efcbcf14e7f13209-Paper-Conference.pdf) · [PersonaMem](https://arxiv.org/abs/2504.14225) · [PersonaMem-v2 preprint](https://arxiv.org/abs/2512.06688)

**Preference changes.** HorizonBench gave models six months of simulated conversation with life events that implied preference changes. Across the 25 models it tested, errors leaned toward the old preference. For two models, selecting the relevant conversations yielded no accuracy gain. Adding an explicit statement of the change improved accuracy by 11 to 22 percentage points. Memora also found frequent reuse of invalid memories and introduced a metric that penalizes it. Hyper-Bot should replace active records when the owner corrects them and treat implied changes as a reason to ask. [HorizonBench preprint](https://arxiv.org/abs/2604.17283) · [Memora preprint](https://arxiv.org/abs/2604.20006)

TransMem tests a retrieval system that identifies explicit changes and stores them as topic-linked records. Hyper-Bot applies the same idea at a smaller scale with stable topics and one active value per topic. The review step makes the newest accepted value explicit. [TransMem preprint](https://arxiv.org/abs/2611.10683)

**Retrieval and actions.** Memory Retrieval for Changing Preferences found that a trained selector could outperform embedding-based search on its preference-heavy tasks. Mem0 reported LoCoMo gains with an extraction and update pipeline and tested an optional graph on the same benchmark. Mem2ActBench asked agents to apply remembered context to tool choice and arguments. Its ACL paper found persistent trouble grounding tool parameters across the seven memory frameworks tested. These results justify measuring selection and tool arguments separately. For Hyper-Bot, begin with scope filters, structured keys, and lexical search, and benchmark a local semantic index if those methods miss useful paraphrases. [Memory Retrieval for Changing Preferences preprint](https://arxiv.org/abs/2606.02976) · [Mem0 paper](https://arxiv.org/abs/2504.19413) · [Mem2ActBench, ACL 2026](https://aclanthology.org/2026.acl-long.370/)

The benchmark results come from different histories, models, tasks, and scoring methods. Use them to pick failure cases and baselines. Measure release performance on Hyper-Bot's own chat, voice, hand-off, and connector flows.

## First-party designs

- OpenClaw gives `SOUL.md` the bot's tone and behavior, `USER.md` the user's current preferences, and other memory files the durable facts and dated observations. It replaces changed preferences in the compact profile and can track the old value in dated notes. Its privacy and provenance rules limit when personal memory enters context. This is a direct precedent for keeping persona changes deliberate and personal recall scoped. [OpenClaw Soul](https://docs.openclaw.ai/concepts/soul) · [OpenClaw user model](https://docs.openclaw.ai/concepts/user-model) · [OpenClaw memory provenance](https://docs.openclaw.ai/concepts/memory-provenance)
- MemGPT introduced a distinction between the material in the active context and a larger store the model could consult. Current Letta agents expose inspectable memory through a Git-backed filesystem and support explicit teaching and background consolidation. LangGraph separates thread history from long-term records under application-defined namespaces and describes foreground and background writes. Adopt inspectability and scope, with an admission rule owned by HyperTask. [MemGPT paper](https://arxiv.org/abs/2310.08560) · [Letta memory and dreaming](https://docs.letta.com/configuration/memory) · [LangGraph memory](https://docs.langchain.com/oss/python/concepts/memory)
- ChatGPT exposes controls to review, change, and remove saved memory separately from chat history. It also has temporary modes that can use existing personalization or omit it, with durable writes disabled while the chat remains temporary. Give Hyper-Bot an explicit off state and clear wording about the copies that a delete action affects. [ChatGPT memory](https://help.openai.com/en/articles/8590148-memory-in-chatgpt) · [ChatGPT temporary chat](https://help.openai.com/en/articles/8914046-temporary-chat-in-chatgpt)

## Design for Hyper-Bot

**Keep one source for Soul.** The settings dialog already edits each bot's `instructions`, and `HyperBotsRuntime.seed` puts that value in the system message. Introduce Soul through that field or migrate it once with exact value preservation, including empty values and the shipped Scout and Scribe instructions. Keep the editor owner-controlled. Let the owner change tone, response format, role, and workflow defaults. Treat an assistant-written Soul revision as a preview until the owner saves it. Keep tool grants and approvals in the existing runtime settings and executor. [Bot settings editor](../src/renderer/features/hyper-bots/HyperBotSettingsDialog.tsx) · [Bot defaults](../src/shared/HyperBots.ts) · [Run seed and tool execution](../src/main/HyperBotsRuntime.ts)

**Store editable records in main.** Use a bounded, versioned collection in the existing account store or an account-local companion file if measured write size warrants it. For each record, keep a stable ID, kind, normalized key when available, plain-text value, scope, source kind and reference, observed and updated times, status, and an optional expiry. A stable key such as `reply.format` lets the app replace one active value within a scope. Limit retained superseded history and exclude it from ordinary recall. The editor should show the value, scope, and source and support editing and forgetting. Point to the original message as long as it is still available, since room history can be pruned. Validate legacy state without requiring new fields. Use atomic changes, revision checks for concurrent edits, and idempotency for saves retried after a reconnect. [Account store and retention](HYPER_BOTS.md#where-things-live) · [Atomic store writes](../src/main/HyperBotsStore.ts)

**Derive scope before ranking.** Main already verifies the signed-in account through the Rust core. Project tools also verify the active workspace. Derive eligible memory from those identities plus the run's bot and room. Use a private scope for direct-room saves and a room scope for group saves with an explicit audience in the UI. Require an owner choice to widen either. Honor the workspace boundary for project memory and skip it when main cannot verify the workspace. Use the receiving bot's scope on a hand-off and exclude private data from group prompts and hand-off text. A narrower active preference can override a broader one for that context. A one-turn request can override either without changing the stored value. Ask on material ambiguity. [Account resolution](../src/main/HyperBotsHub.ts) · [Project workspace checks](../src/main/HyperBotsProjectCore.ts) · [LangGraph namespaces](https://docs.langchain.com/oss/python/langchain/long-term-memory)

**Retrieve at the model boundary.** Keep the current request and recent history in their existing roles. Resolve active revisions, then select a few entries by exact key, task relevance, and recency within the eligible scopes. Drop irrelevant matches and allow an empty result. Place retrieved values in a short, structured block marked as remembered data in the existing user-context message. Use a fixed size budget that leaves room for the current request, existing history, and tool calls. Assemble it in Electron main before invoking the existing engine so Chat Completions and Responses use the same policy. Keep search on device initially. The configured model endpoint still receives any context selected for a turn, which should be clear in the Memory settings. An activity view can show the owner which records the app supplied to the model and link to the editor. [Runtime prompt assembly](../src/main/HyperBotsRuntime.ts) · [Endpoint adapter](../src/main/HyperBotsEngine.ts) · [LongMemEval retrieval experiments](https://proceedings.iclr.cc/paper_files/paper/2025/file/d813d324dbf0598bbdc9c8e79740ed01-Paper-Conference.pdf)

**Make changes effective on resume.** The existing run transcript persists the seed and resumes after approval or restart. Keep recalled memory bodies out of that stored seed. Store selected IDs and revisions for a run, then recheck them and the active scope before each model call. Drop rows that were edited, forgotten, expired, or are no longer in scope. Before a write dispatch, recheck the revisions and scope used to generate the call. Require a fresh turn or explicit review if any of those inputs became ineligible. Forget should remove retained versions and derived index or cache entries, and block re-creation by a stale suggestion or retry. Explain that a past reply or provider request may contain a copy. A Memory-off mode should disable durable reads and writes while preserving the room's normal conversation history. [Run recovery](../src/main/HyperBotsRuntime.ts) · [Stored run transcript](../src/main/HyperBotsStore.ts) · [ChatGPT deletion behavior](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)

## Preventing memory poisoning

MINJA demonstrated that ordinary query access to an agent can lead to poisoned persistent records. The 2026 MPBench preprint found that aggressive write and retrieval policies made the tested agents easier to compromise. MemSecBench tested persistence, consequences in a later task, and selective repair as distinct events. The authors reported malicious content persisting in 84.2% of cases across their 24 tested configurations, with 50.3% completing the full path to an unsafe effect. Those rates describe their setups. Hyper-Bot should test each stage against its own policy. [MINJA, NeurIPS 2025](https://proceedings.nips.cc/paper_files/paper/2025/hash/42a97bbd9844d2bf68596730af80bcdf-Abstract-Conference.html) · [MPBench preprint](https://arxiv.org/abs/2606.04329) · [MemSecBench preprint](https://arxiv.org/abs/2607.27080)

- First release saves through an owner-facing editor or explicit confirmation that shows the exact value and its scope. Main authenticates the account and validates source, scope, shape, and size. Model output, quoted material, other bots, interactive card payloads, and connector data have no write authority. In a later suggestion workflow, derive suggestions from eligible owner turns, retain supporting source IDs, and keep drafts out of recall. Reject secrets, operational instructions that try to change authority, and sensitive connector content at admission. Preserve source lineage through any summaries or imports. [OpenClaw provenance](https://docs.openclaw.ai/concepts/memory-provenance) · [MemLineage preprint](https://arxiv.org/abs/2605.14421)
- A recalled preference can shape tone or supply a low-risk default. Tool permissions, approval state, identities, and connector destinations come from trusted runtime state and the current authorization path. Treat remembered addresses, item IDs, and project targets as candidates that need live verification and the applicable owner decision, including a case where an action would disclose private memory. Keep memory controls off external connector tools and hand-offs. Prompt labels help the model interpret data. Main process checks enforce the boundaries even when a model follows the wrong text. [Hyper-Bot approval checks](../src/main/HyperBotsRuntime.ts) · [CaMeL paper](https://arxiv.org/abs/2503.18813) · [OWASP prompt injection prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

## What to measure before enabling learning

Compare the existing room history, the same history with saved-memory retrieval, and an oracle run that receives only the correct eligible records as its memory input. Keep the model, endpoint route, turn, and tools constant across the comparison. The oracle estimates how much error remains when selection is correct. Run deterministic store and runtime tests with an engine stub before provider evaluations. Use fake Jira, Outlook, and project connectors. Record selected IDs and revisions, answer quality, actual tool name and arguments, approval behavior, context size, and the change in median and tail latency. Keep evaluation logs clear of private memory text. [LongMemEval](https://proceedings.iclr.cc/paper_files/paper/2025/file/d813d324dbf0598bbdc9c8e79740ed01-Paper-Conference.pdf) · [Mem2ActBench](https://aclanthology.org/2026.acl-long.370/) · [HEAMS preprint](https://arxiv.org/abs/2611.20144)

| Case | Expected result |
| --- | --- |
| Owner saves a reply format, starts a fresh chat, and changes model | Eligible bot uses the format when relevant. With an unrelated request, the preference is absent from model input or unused as appropriate. |
| Owner changes that format, overrides it for one turn, then forgets it | The update wins in its scope, the override lasts one turn, and subsequent recall excludes the forgotten value after restart and retry. Retain a separate fixture for historical wording that still appears in room history. |
| Same key in two accounts, workspaces, bots, or rooms | Only eligible records reach the engine. Repeat with a group, hand-off, voice request, account switch during a run, and workspace switch before an approval resumes. |
| Active preference conflicts with an older record or weak inference | Current confirmed value wins. With no confirmed value and a consequential choice, the bot asks or uses the ordinary app default as appropriate. |
| Untrusted tool or bot text proposes a durable setting or an external action | No active write. No memory-derived grant or unauthorized dispatch in the current turn or a later session. Valid unrelated memories still work after selective removal. |
| Owner turns Memory off, or the engine retries through the other endpoint route | The off state reads and writes no durable memory. With Memory on, both routes carry the same eligible data and the retry creates no duplicate records. |

Require zero cross-scope recall, unauthorized memory writes, forgotten-record retrieval, or unauthorized tool execution in the deterministic fixtures. In provider evaluations, track applicable preference following, stale preference use, inappropriate personalization, and correct abstention separately. Test English and Hebrew, with both explicit preferences and paraphrases. Ship owner-managed Soul and Memory first. Use measured recall misses and the correction and isolation tests to decide whether to add automatic suggestions or semantic search. [PrefEval](https://proceedings.iclr.cc/paper_files/paper/2025/file/28a46044775d97a4efcbcf14e7f13209-Paper-Conference.pdf) · [HorizonBench](https://arxiv.org/abs/2604.17283) · [MemSecBench](https://arxiv.org/abs/2607.27080)
