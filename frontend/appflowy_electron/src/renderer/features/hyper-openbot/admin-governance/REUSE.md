## API families and shared ownership

Only the `admin-governance` registry and allowlist slot lines are changed. The registry lazily loads `HyperGovernanceSection` in group `admin`.

Added families: `me`, `admin/people`, `admin/enterprise`, `admin/identity-providers`, `admin/audit-events`, `admin/what-if`, `auth/sso/register`, `computers/policy`, `computers/policy-dry-run`, `computers/policy-translate`. Existing `capabilities` and `approvals` families supply deployment edition and team/shared-use/guidance routes. Two appended `admin-governance` policy test blocks cover allowed and refused adjacent/escaped paths. No other shared files are modified.

Calls include people list/role/access; enterprise overview, capability PUT, capability translate/preview/batch, SSO/recording setting PUT, action records and member computer termination; identity provider list/delete and SSO register; policy GET/PUT/translate/dry-run; audit list/ask/vocabulary/CSV; what-if vocabulary/ask/check/explain; approvals inbox/team PATCH, team rule POST/PATCH/DELETE/translate/backtest/batch, shared-use list/approve/decline, guidance GET/PUT/DELETE/check and GET/POST backtest.

## Native adaptations and integration boundaries

Pages use local navigation and disclosure panels instead of upstream TanStack URLs/dialogs. Form drafts and user-entered secrets exist only in React state and request bodies. Provider secrets are cleared on submission completion, protocol changes, explicit clearing and unmount. Error text never echoes remote response bodies. Server role checks and server save-time validation remain authoritative. No credentials are read from storage; no shell, global CSS, CSP or Electron security changes are introduced.

The native section context exposes conversation actions only, so links from verdicts to Apps/Computers and the overview's other specialists' pages cannot programmatically select those registry sections. Those sections are reached through the native section selector. The three verdict destinations owned here navigate locally. This is a shared-navigation interface limitation, not a missing governance API flow. External identity account-linking belongs to Settings; no assigned admin route calls those personal identity APIs.

Validation uses Node 24 and the existing locked dependency tree. No live backend, Electron launch, deployment action, credentials, push or PR is involved. Automated verification covers contracts and server-rendered presentation; live role/account/provider state is intentionally not exercised.
