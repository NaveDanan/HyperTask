# HyperTask Outlook security review

Reviewed 2026-11-17 against repository code and current primary-source documentation. This is a code/docs review, not a penetration test or security certification. No Outlook process was started and no mailbox or user message contents were accessed. The separate three-email demo is outside this review.

## Assessment and observed controls

This is legitimate local automation with useful safeguards, but its underlying authority is broad. It cannot be described as a read-only or calendar-scoped security boundary. Whether deployment is acceptable depends on endpoint controls, renderer integrity, authorization, and company policy.

[HyperOutlookBridge.ts](D:/Projects/HyperTask/frontend/electron/src/main/HyperOutlookBridge.ts:38) writes a UUID-named script in `%TEMP%`, then launches hidden Windows PowerShell with `-STA -ExecutionPolicy Bypass -File`; JSON travels through stdin/stdout pipes. [HyperOutlookIpc.ts](D:/Projects/HyperTask/frontend/electron/src/main/HyperOutlookIpc.ts:7) checks the main window/main frame and allowlists operations; [HyperOutlookSchema.ts](D:/Projects/HyperTask/frontend/electron/src/main/HyperOutlookSchema.ts:14) validates arguments with Zod. These reduce accidental misuse and injection exposure; they do not establish user intent.

[HyperOutlookScript.ts](D:/Projects/HyperTask/frontend/electron/src/main/HyperOutlookScript.ts:10) creates `Outlook.Application`, obtains `MAPI`, selects calendar folder 9, and checks appointment class/calendar membership when resolving IDs. It nevertheless retains the broader Outlook object model and supports create/update/delete/send/respond. [Renderer confirmations](D:/Projects/HyperTask/frontend/electron/src/renderer/features/hyper-outlook/HyperOutlookEventDialog.tsx:54) become caller-supplied `send` booleans. [Window preferences](D:/Projects/HyperTask/frontend/electron/src/main/index.ts:109) enable context isolation and disable Node integration, but explicitly disable the renderer sandbox.

## Documented platform behavior

**Object Model Guard and trust.** Microsoft's [security behavior guidance](https://learn.microsoft.com/en-us/office/vba/outlook/how-to/security/security-behavior-of-the-outlook-object-model) describes warnings for protected entry points, not per-app OAuth scopes. This helper is a cross-process COM caller. Under documented default/policy conditions, Outlook suppresses warnings when Windows reports acceptable antivirus health. Trust Center/Group Policy can change behavior; “Always warn” and “Never warn” exist, with the latter not recommended. No actual AV status or enterprise policy was inspected. Absence of a prompt proves neither safety nor narrowly granted consent.

Microsoft's [protected entry-point list](https://learn.microsoft.com/en-us/office/vba/outlook/how-to/security/protected-properties-and-methods) includes these **MailItem** properties: `Bcc`, `Body`, `Cc`, `HTMLBody`, `PropertyAccessor`, `ReceivedByName`, `ReceivedOnBehalfOfName`, `Recipients`, `ReplyRecipientNames`, `RTFBody`, `Sender`, `SenderEmailAddress`, `SenderEmailType`, `SenderName`, `SentOnBehalfOfName`, and `To`; protected methods include `SaveAs` and `Send`. `Subject` and `ReceivedTime` are not listed. Calendar `Body`, `Organizer`, `Respond`, and `Send` are also protected. Read-only body/sender retrieval can therefore encounter guard warnings, depending on trust/policy; do not disable protections to make a demo work.

**Scope and compatibility.** [GetDefaultFolder](https://learn.microsoft.com/en-us/office/vba/api/outlook.namespace.getdefaultfolder) selects a folder for the current profile; selecting Calendar does not restrict the COM application's capabilities. There is no per-app read-only/calendar-only permission grant in this design. Microsoft's [classic/new Outlook comparison](https://support.microsoft.com/en-us/office/feature-comparison-between-new-outlook-and-classic-outlook-de453583-1e76-48bf-975a-2e9cd2ee16dd) lists OOM as available in classic Outlook and unsupported in new Outlook.

**PowerShell.** Microsoft states that [execution policy](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1) is not a security boundary. `Bypass` removes that policy's blocking/prompts for the process; it does not override MachinePolicy/UserPolicy Group Policy. Hidden execution and STA are not isolation or permission controls.

**Graph alternative.** The delegated [permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference#mailreadbasic) distinguishes `Mail.ReadBasic` (excludes bodies, previews, attachments, extended properties), `Mail.Read` (reads the signed-in user's mailbox), and `Mail.ReadWrite` (adds create/update/delete; does not itself permit sending). `Mail.Send` is separate. Prefer delegated basic access for metadata; body reading needs `Mail.Read`, without write/send scopes. This grants broader reading than three messages: API limits are additional application controls. Graph is not a blanket on-premises substitute: Microsoft documents that [hybrid REST access to on-premises mailboxes ended in July 2023](https://learn.microsoft.com/en-us/graph/hybrid-rest-support). Confirm mailbox location and supported access with IT.

## Conditional risks and prioritized recommendations

A compromised authorized renderer could submit valid write/send requests; schema and sender checks would not distinguish them from clicks. A process able to modify the temporary script before PowerShell opens it could substitute code; UUID naming reduces collision/prediction, not write authority. These are threat scenarios, not demonstrated exploits.

1. **Authorize writes in main.** Default to read-only. Require main-owned native confirmation using canonical item/action/recipient details for writes, deletes, invitations, cancellations, and responses. Bind approval to the exact operation and payload; consume it once. A renderer `send: true` is insufficient.
2. **Restore sandboxing where feasible.** Audit/bundle preload dependencies, retain context isolation, narrow IPC, and test `sandbox: true`. [Electron's official guidance](https://github.com/electron/electron/blob/main/docs/tutorial/sandbox.md) explains the sandbox's resource restrictions and risks of disabling it. Sandboxing still requires IPC authorization.
3. **Harden helper integrity/lifecycle.** Prefer a protected installed helper over writable temporary executable scripts. If temporary scripts remain, use exclusive creation, restrictive Windows ACLs, bounded lifetime, and cleanup on exit/error/timeout plus stale-file recovery. Same-user malware remains outside what user-only ACLs can isolate. Respect enterprise signing/execution policy.
4. **Expose minimal email reads.** For the demo, allow only a fixed Inbox read, maximum three messages, explicit fields and bounded text, with no attachments, generic COM dispatch, read-status updates, save/delete/respond/send, or automatic forwarding. A COM API allowlist reduces exposure but cannot reduce COM's underlying profile authority. Graph supports [field/page limits and text-body preference](https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0).
5. **Treat messages as hostile data.** Display body text; load no external resources or active HTML. Never trust email instructions as AI/tool authorization. Avoid content logging or uploads without explicit consent. Keep Outlook/Electron/Windows and managed AV current; verify policy with IT.

Local Electron IPC and child pipes are not internet encryption. Outlook handles server transport according to account/server configuration; this review did not verify transport security or end-to-end encryption.

## Local verification by the parent task

- The session is running as the same normal Windows user, without administrator elevation, and classic Outlook is already running. No Outlook security or antivirus settings were changed.
- The existing mocked IPC/bridge checks passed: **2 test files, 11 tests** (`vitest run src/main/HyperOutlookIpc.test.ts src/main/HyperOutlookBridge.test.ts`). They cover caller/frame rejection, input validation, bridge failures and related behavior; they do not prove resistance to a compromised authorized renderer.
- Added the standalone [HyperOutlookMailDemo.ps1](D:/Projects/HyperTask/frontend/electron/scripts/HyperOutlookMailDemo.ps1:1). It selects only the default Inbox, sorts by received time descending, returns at most three MailItem messages, reads bounded plain-text previews, and compares each message's unread flag before/after. It has no mail-write, send, display, attachment, or external-network operation. PowerShell syntax validation passed. Message data is not written to a file.
- Initial Windows PowerShell `-File` execution was blocked before the demo ran. All Windows PowerShell execution-policy scopes were `Undefined`; its effective default is `Restricted`. The separate PowerShell Core host reports `RemoteSigned`, which does not establish the Windows PowerShell host's effective policy.
- After the user explicitly approved the one-time process-scoped `-ExecutionPolicy Bypass` invocation, the demo completed successfully on 2026-11-17 using classic Outlook COM/MAPI. It returned the three newest MailItem messages from the default Inbox, including sender, subject, received time and a plain-text preview of up to 400 characters. All three messages retained their original unread flags (`AllReadStatesUnchanged: true`). No mail was sent, saved, moved, deleted, displayed, or marked read; no attachments or message links were opened. The Windows PowerShell execution policy in a fresh process remains `Restricted`. No Outlook Object Model Guard settings or antivirus settings were changed. Message contents are intentionally omitted from this repository report.
